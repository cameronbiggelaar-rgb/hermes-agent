## 1. Fault B — what actually broke

### 1.1 Observed event (2026-11-03, gateway cutover stop)

| phase | measured |
|---|---|
| pre-drain `mark_resume_pending` + notify | **6.32 s** |
| drain (`restart_drain_timeout`) | **180.01 s**, `timed_out=True`, 1 agent |
| interrupt + settle | 3.14 s |
| kill tool subprocesses + finalize + quiesce | 4.45 s |
| SessionDB close | 0.05 s |
| **total stop** | **193.61 s** |

The drain spent its entire 180 s budget and returned `timed_out`, i.e. the agent never finished —
the "graceful" drain degraded to "wait the full budget, then interrupt". The stop then needed 13.6 s
more. Against the unit file's `TimeoutStopSec=210` that leaves 16 s of slack, and every remaining
phase (settle alone is budgeted 45 s + a 10 s tail reserve) is unbudgeted inside it.

That is the defect: **the drain budget is not a share of the stop envelope, it is the whole
envelope plus whatever the teardown happens to cost.**

### 1.2 Root cause

`resolve_systemd_timeout_stop_sec(drain, cron_floor)` sized the unit as `drain + 30 s`. Systemd's stop
clock starts at SIGTERM and covers drain **and** interrupt **and** settle **and** finalize **and**
quiesce **and** SessionDB close. A 30 s headroom is smaller than `settle_gateway_runtime`'s own 45 s
settle budget, so a unit generated by this very function could be "correct" and still be SIGKILLed
mid-settle. The 300 s `95-timeout-stop.conf` drop-in hid this for the cutover; it did not fix it, and
any host without that drop-in still carried the defect.

Second half of the defect: nothing clamped the drain against the *live* unit. `drain_control` and
`effective_stop_drain_timeout` only honoured launchd's `ExitTimeOut`. Under systemd — including a
stale, hand-edited or older unit — a drain larger than the envelope is accepted without question.

### 1.3 Reproduction (deterministic, no restart required)

`harness/fault_b_repro.py` replays the measured phase costs against the real budget functions in
`gateway/restart.py`. Worst-case phase budgets are the code's own: notify 15 s, settle 45 s, finalize
15 s, close 10 s.

| case | unit | drain | total | margin | verdict |
|---|---|---|---|---|---|
| pre-fix / shipped | 210 | 180 | 265.00 | −55.00 | **SIGKILL** |
| pre-fix / drop-in | 300 | 180 | 265.00 | +35.00 | fits |
| pre-fix / regenerated | 300 | 180 | 265.00 | +35.00 | fits |
| post-fix / shipped (stale unit) | 210 | 120 | 205.00 | +5.00 | fits |
| post-fix / drop-in | 300 | 180 | 265.00 | +35.00 | fits |
| post-fix / regenerated | 300 | 180 | 265.00 | +35.00 | fits |

Observed-cost rows (6.32 / 180.01 / 3.14 / 4.45 / 0.05) reproduce the historical 193.6 s stop and fit
in every case; the model is calibrated to the journal, not to a guess.

What this does **not** prove: that the kernel never sends SIGKILL. That needs a real stop of the
real service, which is owner-gated. §5 states the exact release test.

### 1.4 The correction (smallest durable change, 4 files)

1. `gateway/restart.py`
   - `SYSTEMD_STOP_HEADROOM_S 30.0 → 120.0` — sized from the sum of the post-drain phase budgets
     (85 s) with margin, not from intuition. Side effect: the generated unit for the shipped
     180 s drain is now **300 s**, exactly the value that carried the cutover — so retiring the
     drop-in changes no runtime behaviour.
   - `SYSTEMD_POST_DRAIN_RESERVE_S = 90.0` — what the live unit must still hold after the drain:
     settle 45 + tail 10 + quiesce/close 7.1 + margin.
   - `resolve_systemd_capped_drain(drain, timeout_stop_s, reserve)` — caps the drain at
     `unit − reserve`; fail-open on unknown/non-finite/≤0 budgets; a unit smaller than the reserve
     yields drain 0 (interrupt immediately) instead of a guaranteed SIGKILL.
   - `effective_stop_drain_timeout()` and `effective_stop_watchdog_delay()` now apply that cap under
     systemd (the watchdog leash gets a 5 s dump margin so forensics land before SIGKILL).
2. `gateway/run_runtime_init.py` — `self._systemd_timeout_stop_sec: Optional[float] = None`.
3. `gateway/run_startup.py` — records the live `TimeoutStopUSec` from the existing alignment probe.
4. `gateway/run_shutdown.py` — the drain-cap warning and the shutdown snapshot now name the live
   systemd budget, not just launchd's.

Tests: `tests/gateway/test_stop_budget_adaptation.py` (new) pins both halves — the generator leaves
≥ reserve, and the runtime clamps to the live budget. `test_cron_drain_floor.py`,
`test_gateway_service.py`, `test_shutdown_forensics.py` expectations were realigned to the new
headroom. Targeted suites: **193 passed, 4 skipped**, 1 failure + 2 errors that are
pre-existing/environmental (see §7).

### 1.5 When `95-timeout-stop.conf` can be retired

Retirement is safe when **all four** hold:

1. The fixed code is installed (generator emits `TimeoutStopSec=300` for a 180 s drain / 30 s cron
   floor, i.e. the same ceiling the drop-in provides).
2. `systemctl show -p TimeoutStopUSec hermes-gateway.service` reports `300000000` with the drop-in
   removed — proving the value now comes from the unit, not the override.
3. One owner-approved restart completes the shutdown-alignment gate
   (`shutdown_alignment_gate.py --unit hermes-gateway.service`) with no SIGKILL and a stop time
   inside the new envelope.
4. Rollback is one file: re-add the drop-in and `daemon-reload`.

Until (1) is deployed, removing the drop-in reverts to 210 s, which the model above shows is overrun
by 55 s on the worst case. **Retirement must follow deployment, never precede it.**

## 2. Interrupted sessions — reconciliation

### 2.1 The arithmetic, exactly

Cutover epoch: `2026-11-03 19:40:20 +11:00` (= `1793695220`).

| movement | count | evidence |
|---|---|---|
| open at cutover (receipt) | 508 | RESTORE-001 receipt |
| ended after cutover, started before | **10** | `end_reason='startup_orphan_reap'`, all at 21:41:11 local |
| created after cutover | **2** | both `source='cron'` |
| ended after cutover, started after | **2** | `end_reason='cron_complete'` |
| open now | **498** | `SELECT count(*) … WHERE ended_at IS NULL` |

`508 − 10 (reaped) + 2 (created) − 2 (completed) = 498`. The reported "12 normal completions" is the
sum of both `end_reason` groups — 10 `startup_orphan_reap` + 2 `cron_complete` — and the "net −10"
is the reaped ten. The two new sessions are cron runs that opened and closed after the cutover; they
never belonged to the pre-cutover population. **The reconciliation closes with no unexplained rows.**

### 2.2 Classification of the 498 (live, read-only)

Via `python -m gateway.session_resume_plan` against `~/.hermes/state.db` + `sessions.json`:

| bucket | count | meaning |
|---|---|---|
| `active` | 5 | live Telegram threads, activity inside the 6 h grace (this session among them) |
| `obsolete` | 492 | open rows with no resume marker: 485 with messages, 7 empty — never closed by pre-cutover CLI/TUI paths |
| `needs_human` | 1 | `20261101_114213_465a52f1`: routing entry names a different `session_id`, 0 messages |
| `resumable` | **0** | — |

Whole-DB picture: 2 213 completed, 498 open, 2 711 total.

### 2.3 The finding that changes the risk model

`resume_pending` is **false on every row in the DB**:

- `gateway_routing`: 2 541 rows, 0 with `resume_pending=true`.
- `sessions.json`: 1 287 entries, 0 with `resume_pending=true`.

Resumption is gated on `entry.resume_pending AND entry.resume_reason IN {restart_timeout,
shutdown_timeout, restart_interrupted} AND NOT suspended`, and then on a **1 h freshness window**
(`_AUTO_CONTINUE_FRESHNESS_SECS_DEFAULT`) — a marker older than an hour is a dead letter regardless.

**Correction to an assertion made earlier in this work:** I said the first start after releasing the
hold "would attempt to resume ~498 sessions". That is wrong. Releasing the hold today would resume
**zero** sessions: there is no marker to act on, and any 2026-11-03 marker would be stale by an order
of magnitude. The hold remains valuable as a control (it makes the next interruption explicit), but
it is not the only thing standing between the host and a resumption storm, and the 498 number is
"rows never closed", not "turns interrupted".

### 2.4 The bounded recovery mechanism

`gateway/session_resume_plan.py` — a planner with no side effects (read-only DB handle, prints JSON,
resumes nothing):

- **Evidence-first classify** → completed / active / resumable / obsolete / needs_human. A row is
  `resumable` only with a live, fresh, recognised marker; an unroutable mismatch is `needs_human` and
  is never batched.
- **Identity checks** — routing `session_id` must equal the row id; unknown ids are skipped.
- **Explicit selection** — `--request <session_id>` per session. The planner never expands a bucket,
  so clearing the hold cannot become "resume everything".
- **Fail-closed on the hold** — the CLI assumes the hold is active; `--assume-hold-released` is the
  only way to plan without it, and even then nothing is resumed.
- **Concurrency + total limits** — `batch_size` (default 5) per batch, `max_total` (default 25).
- **Memory-pressure stop** — refuses outright below `MemAvailable < 1.5 GiB`, and stops mid-plan
  when the projection for the next batch would cross the floor (64 MiB per session).
- **Idempotent** — `--already-resumed` skips work already done; re-planning the same input yields
  the same batches minus completed work.

Tests: `tests/gateway/test_session_resume_plan.py`, **11 passed**, covering every rule above plus the
live-shape fixture (routing join, TEXT timestamps, index merge).

## 3. Adversarial self-review

| attack | answer |
|---|---|
| "You tuned 30 → 60 → 90 → 120 until the numbers passed." | The final value is derived from the sum of the phase budgets the code itself sets (85 s), not from a target percentage; 90 was rejected because it left 5 s on the worst case. The value also lands on 300 s, which is independently corroborated by a real stop. |
| "The model is not a SIGKILL proof." | Correct, and §5 does not claim otherwise. It is calibrated on the one real stop (193.6 s) and the defect assertion (210 < 265) depends only on the code's own budgets, not on my timing estimates. |
| "Capping the drain could cut a legitimately slow turn short." | The cap only binds when the unit is smaller than drain + reserve — i.e. when the current behaviour is a guaranteed SIGKILL. Under the regenerated unit the cap never binds (`resolve_systemd_capped_drain(180, 300) == 180`), asserted by `generator_self_consistent`. |
| "Fail-open on unknown budgets hides the defect." | Unknown means "not under systemd, or the probe failed": preserving the configured drain is the pre-existing behaviour and the safe default. A *known* small unit is not fail-open — it gets drain 0. |
| "The planner is dead code; the gateway will never call it." | Deliberate. Activation is the owner's decision and needs the identity checks run against live state, not a stored plan. The planner's value now is the classification evidence in §2 and a pre-flight for any future release. |
| "Calling 492 rows `obsolete` is a data-loss euphemism." | `obsolete` here means "open row with no resume marker"; nothing is deleted, ended or pruned. The 7 empty ones are candidates for a future owner-approved tidy-up, not this package. |
| "The 5 `active` sessions include yours, so the classifier is just recency." | It also requires no marker and no lease; the 6 h grace matches `session_viewer_close.STARTUP_IDLE_S` so the buckets agree with the gateway's own orphan sweep. |
